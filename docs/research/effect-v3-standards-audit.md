# Effect v3 standards audit

This audit is evidence for the copyable TypeScript profile. It applies to the
versions resolved by `testers/ts/bun.lock`, not Effect `main` or Effect v4.

## Evidence labels

- **VERIFIED FACT**: established by the pinned declarations, implementation, or
  official Effect v3 source.
- **EMPIRICAL RESULT**: observed in a deterministic probe against the pinned
  installation.
- **REASONED INFERENCE**: a conclusion drawn from verified behavior and an
  explicit application contract.
- **STYLE PREFERENCE**: a default chosen for consistency, not a correctness
  property.

## Pre-edit contradiction report

1. **Pinning versus dependency declarations.** Pre-edit lines 164-169 said
   to pin exact versions, but `TS/package.json` used caret ranges and `bun.lock`
   was not in the TypeScript mirror. A copied project could install untested
   Effect and language-service versions.

2. **Platform diagnostics versus absent platform implementation.**
   `globalFetch`, Node built-ins, console, time, timers, random, crypto, and
   environment diagnostics became blocking under strict CI while the baseline
   depended only on `effect`. Agents were told to use replacements the profile
   did not supply.

3. **Bun-only versus generic UI.** The profile said Bun-only while pre-edit
   lines 110-125 prescribed screen and component lifecycle rules spanning
   browser, mobile, SSR, and framework runtimes with materially different
   ownership models.

4. **Run only at explicit edges versus direct writes.** Pre-edit lines 18-22
   prohibited runners in reusable logic; lines 118-119 directed every UI write
   through the default `Effect.runFork` without an application runtime edge.

5. **Fork owner versus detached write.** Pre-edit lines 29-31 required an owner
   and shutdown policy; lines 118-119 created detached default-runtime work and
   specified neither failure observation nor shutdown or disposal.

6. **Log cause versus protect provider details.** Pre-edit lines 58-59 mandated
   cause logging; lines 63-64 said provider, driver, and stack detail in `cause`
   must never reach a readable log. The selected error constructor serializes
   supplied fields by default.

7. **Scope as leakage versus Effect's explicit lifetime type.** Pre-edit lines
   99-101 correctly described `acquireRelease` sharing `Scope`; lines 107-108
   then called a caller-visible close or Scope requirement a design failure.

8. **Pure TypeScript remains plain versus global Effect-native blocking.**
   Pre-edit lines 3-6 preserved pure TypeScript, while configured `asyncFunction`,
   global time, console, fetch, timers, random, environment, `newPromise`, and
   Node import diagnostics applied across included source and tests. The profile
   turned a preference into a global gate.

9. **Test only undocumented semantics versus reliance on runtime behavior.**
   Pre-edit lines 145-149 rejected tests for documented behavior while the
   standards relied on cancellation, retry counts, timeout order, finalizer
   behavior, fiber lifetime, and layer memoization that the compiler cannot
   establish.

10. **Fixture uses `Effect.fn` versus no function-shape standard.** The
    pre-edit canonical fixture used `Effect.fn`, but lines 23-25 mentioned only
    `Effect.gen` and `pipe`; agents received no rule for names, spans, public
    channel pinning, or `fnUntraced`.

11. **Deadline stops work versus admitted non-cancellation.** Pre-edit lines
    73-75 claimed a deadline stopped the real request; lines 76-82 admitted
    signal support might cover only part or none of the exchange.

12. **Compose once at root versus feature, request, and test scopes.** Pre-edit
    lines 49-50 collapsed provisioning into one application root while resource
    guidance implicitly required request and operation scopes.

13. **Explicit service form claimed superior versus exact API facts.** The
    preference was defensible because `Effect.Service` is experimental in
    3.22.0, but test replaceability and accessor support exist across
    alternatives; the old rationale overclaimed.

## Pre-edit verdict

The strongest material was channel precision, lazy Effect construction,
avoiding runners in services, scoped resource construction, partial
cancellation caveats, and behavioral boundary tests. Those strengths were
outweighed by detached writes, cancellation/retry conflation, duplicate and raw
cause logging, incorrect Scope erasure, universal timeout folklore, and UI
rules embedded in a Bun-only core.

**Pre-edit grade: D.** It was not safe as a baseline for largely autonomous
agents: several of its simplest and most confident instructions were wrong at
the exact points where runtime ownership and distributed-operation semantics
must be explicit.

### Suppression findings

- **VERIFIED FACT**: the parser accepts section directives and next-line
  directives in the forms `@effect-diagnostics` and
  `@effect-diagnostics-next-line`; an optional `effect/` prefix and `*`
  wildcard are accepted. Levels include `off`, `error`, `warning`, `message`,
  `suggestion`, and `skip-file` (`cli.js:30023-30068`).
- **VERIFIED FACT**: every emitted diagnostic offers both a rule-specific
  next-line suppression and a whole-file suppression (`cli.js:30087-30123`).
  These generated comments contain no reason, dependency owner, version, or
  removal condition. They are unsafe as an agent's default quick fix.
- **VERIFIED FACT**: only unused next-line directives are detected. The default
  `missingDiagnosticNextLine` severity is `warning`; section overrides,
  wildcards, and `skip-file` directives have no equivalent stale-suppression
  check (`cli.js:30155-30184`).
- **EMPIRICAL RESULT**: without `--strict`, the default unused-next-line warning
  is visible but exit-zero. The final configuration sets
  `missingDiagnosticNextLine: "error"`; its permanent fixture proves that the
  standalone command exits nonzero. Version 0.87.1 reports this plugin-level
  diagnostic with the synthetic name `effect(-1)`, another pinned discrepancy.
- **REASONED INFERENCE**: ordinary source MUST use a rule-specific next-line
  suppression only. The adjacent comment must name the false positive, explain
  why the operation remains safe, identify the owning dependency and exact
  version, and state the removal condition. Wildcards, section-wide changes,
  and `skip-file` are reserved for generated code or a dedicated diagnostic
  fixture with an owner.
- **VERIFIED FACT**: `leakingRequirements` has separate semantic escape hatches:
  `@effect-leakable-service` on an intentionally caller-supplied capability and
  `@effect-expect-leaking ServiceName` on the service (`cli.js:38321` and
  `42597`). These are API-contract annotations, not generic suppressions; they
  require a documented lifetime/caller rationale.

## Post-patch executive verdict

The pre-edit profile had several good local instincts and an unsafe system-level
model. Its strongest parts were precise `Effect<A, E, R>` channels, lazy
construction, scoped acquisition, partial cancellation caveats, and tests that
looked beyond return values. Its most dangerous parts were detached UI writes,
retry safety inferred from cancellation, timeout arithmetic presented as a
guarantee, raw/duplicated cause logging, and treating `Scope` in `R` as a design
failure. Its most misleading parts were calling a local diagnostic selection an
Effect-native preset and presenting one service form, one composition root, and
one UI mutation policy as universal idiom. Its largest omissions were runtime
ownership, defect/full-Cause policy, exact retry ownership and idempotency,
bounded concurrency/backpressure, configuration/secrets, safe error projection,
platform shutdown, and executable semantics.

The patched profile is safe as a copyable baseline for largely autonomous
agents within its stated boundary: a private Bun application using Effect v3.
It is not a production architecture in a box. HTTP policy, durable work,
framework integration, observability exporters, and published-library support
remain explicit overlays because pretending those choices are universal would
reintroduce the original defect.

| Assessment                              | Before | After                                                  |
| --------------------------------------- | ------ | ------------------------------------------------------ |
| Grade                                   | D      | B+                                                     |
| Composite safety/agent-legibility score | 3.5/10 | 8.7/10                                                 |
| Autonomous-agent suitability            | No     | Yes, inside the declared profile and enforced workflow |

The remaining 1.3 points are deliberate limits, not hidden completeness claims:
several distributed-systems invariants remain operation-specific manual review,
the fixture uses a controlled fake boundary rather than a real HTTP stack, and
browser/UI/library overlays need their own integration tests when adopted.

## Rejected recommendations

- Rejected “use `ManagedRuntime` for every background task.” It owns a layer and
  runtime disposal, but `runFork` is still not an application task registry.
- Rejected direct default-runtime `runFork` for writes and rejected the
  read/write cancellation dichotomy. Ownership and commit semantics decide.
- Rejected blanket Effect-native diagnostics. They combine correctness checks,
  style preferences, runtime assumptions, and v4-only rules.
- Rejected mandatory `@effect/platform` HTTP adoption. The pinned platform
  runtime is used for shutdown; native HTTP remains behind a typed tested
  adapter until a project chooses an HTTP overlay.
- Rejected one service/tag constructor as universally idiomatic.
  `Context.Tag`, `Effect.Tag`, and experimental `Effect.Service` have a decision
  table.
- Rejected erasing every `Scope` requirement and rejected layer construction at
  one process-global root. Lifetime determines the correct root.
- Rejected a Schema for every internal type, sync-Schema bans outside Effect,
  and property tests for every schema.
- Rejected error logging at every layer, raw provider objects in public errors,
  and error logs for every retry attempt.
- Rejected mandatory OpenTelemetry, durable queues, databases, frameworks, or
  generalized job systems in the core fixture. None is needed to prove the
  baseline contracts.
- Rejected automatic retry tables based only on HTTP status, AbortSignal
  support, or user visibility; operation semantics and one owner govern retry.
- Rejected `Effect.disconnect` as a timeout shortcut because it returns before
  cleanup completes without supplying an owner for continuing work.
- Rejected `Layer.mock` as a universal testing default. Explicit test services
  are clearer unless a partial mock's unexpected-call defect is the property
  under test.
